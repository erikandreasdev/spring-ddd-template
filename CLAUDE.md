# Project architecture

All code follows tactical DDD with ports and adapters and the Clean Architecture dependency
rule. These rules are mandatory. If a request conflicts with any of them, say so before
writing code instead of skipping the rule.

## Stack

- Java 21, Spring Boot 4, Maven.
- Persistence with MyBatis (annotation-based mappers) and migrations with Flyway.
- Database: PostgreSQL. <!-- CHANGEME: database -->
- Contract-first API: `src/main/resources/openapi/api.yaml` generates interfaces and models.
- No Lombok or MapStruct: records, constructors and hand-written mapping.
- Formatting: google-java-format. <!-- CHANGEME: format command, or delete this comment if you format from the IDE -->
- Base package: `com.CHANGEME`.

## Package structure

By context first, then by layer:

```
com.CHANGEME
├── shared
│   ├── domain           DomainException, NotFoundException, ConcurrentUpdateException
│   ├── application      UseCase (own annotation, no Spring)
│   └── infrastructure   UseCaseConfig, ClockConfig; web/ (error handling, request logging)
│       └── web/api      code generated from api.yaml (do not edit)
└── <context>            e.g. orders
    ├── domain           aggregates, value objects, IDs, exceptions, *Repository interfaces
    ├── application      use cases, commands, queries, result records, ports
    └── infrastructure
        ├── web          controllers and *ApiConversion conversion classes
        └── persistence  MyBatis mappers, *Row records, repository implementations
```

Dependencies only point inwards: `infrastructure → application → domain`.

## Rules per layer

### domain
- Imports only `java.*` and other `domain` classes. No Spring, MyBatis, Jakarta or Jackson.
- Aggregates protect their invariants through business methods. No setters.
- Aggregates have a private constructor and static factories: a creation factory named in the
  business language (`Order.place(id, ...)`) and `restore(...)` for persistence.
- Typed, positive identifiers: `record OrderId(long value)`. They are generated by a database
  sequence: the use case requests one with `repository.nextId()` before creating the
  aggregate, which is always born with an ID. Never bare `long`s in domain or application
  signatures.
- Every aggregate has a `long version` (optimistic locking): 0 on creation, received in
  `restore(...)`.
- An aggregate references another one only by its ID, never by object.
- Elements of a collection inside an aggregate have no ID of their own.
- Value objects are immutable records validated in their compact constructor.
- One repository per aggregate, as an interface in `domain`: `OrderRepository`.
- The current time comes from an injected `java.time.Clock`; never call `Instant.now()` directly.
- No domain events. If something must react to a change, the use case calls another port.

### application
- Imports only `java.*`, `domain` and `application`. No Spring, Jakarta or logging.
- One class per use case: public, not final, annotated with `@UseCase`, named
  `<Verb><Noun>Service` and with a single public method.
- No input interface: the controller depends on the use case class.
- Input: a `*Command` record (modifies) or `*Query` record (reads), validated in its compact
  constructor. No Bean Validation annotations.
- Output: `void` or the ID for commands; a result record (`OrderSummary`) for queries. The
  aggregate is never returned. No presenters or output boundaries.
- The use case orchestrates (load, call the aggregate, save). Business rules live in the
  domain.
- No `@Service` or `@Transactional`: `UseCaseConfig` registers every `@UseCase` class as a bean
  and wraps its public methods in a transaction.
- Reading an aggregate by its ID: repository plus conversion to the result record.
- Lists, searches and pagination: a read port in `application` (`OrderSummaries`) that returns
  result records directly from SQL.
- Other output ports are interfaces in `application` named after their purpose
  (`PaymentGateway`) and implemented in `infrastructure`.

### infrastructure
- The only place where Spring, MyBatis, Jakarta and logging are used.
- `web`: controllers implement the generated interface and only translate between HTTP and use
  cases. They never use repositories or contain logic.
- `persistence`: implementations of repositories and read ports. The aggregate is never used as
  a MyBatis type.

## Way of working

- Always a plan before touching code, and wait for my approval. The plan states which files
  change, whether the API, the model or the schema change, and whether an ADR is needed.
- Never commit or `push`: changes stay uncommitted so I can review them.
- Never, unless I ask: modify `ArchitectureTest`, `CLAUDE.md` or `.claude/`, edit generated
  code, disable or delete tests.
- Do not add dependencies to `pom.xml` without stating which one and why in the plan.
- Destructive migrations (dropping columns or tables, changing types): always explicit in the
  plan, even if the change looks small.
- If the domain model changes, update its diagram in the same task.
- If I accept an exception to these rules or we choose between real alternatives, record it in
  an ADR in `docs/adr/`. Before proposing anything, review the existing ADRs.
- When done: what changed, the result of `mvn verify` and any deviation from the rules.

## Verification

- Work with TDD: test first, then code (details in `.claude/rules/testing.md`).
- `ArchitectureTest` (ArchUnit) enforces dependencies and naming. It is not modified or
  disabled to make code pass; the code is fixed. A hook runs it at the end of every turn: if it
  fails, fix it before considering the work done.
- A feature is done when `mvn verify` passes (tests and 80% branch coverage). It needs Docker
  running.
